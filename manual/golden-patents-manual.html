Golden Patents Manual1 · What gold means

Chapter 1What gold means and how the work is shaped

The pipeline reads a patent and writes three JSON files: reactions, compounds and pathways. They are a first draft written by a model. Gold is that draft after a second reader has proven it against the patent, line by line.

A record is gold when

  • Everything the patent says about it is in the record.
  • Nothing in the record is unsupported by the patent.
  • Every empty field was checked, and the patent really is silent.
  • Every generated label is right, and consistent across the file.

A file is gold when every record is, and it holds each reaction, compound or pathway the patent describes once. Deliberate exceptions are written down.

Two questions, in order

  1. Coverage. Does the file hold everything the patent describes, and nothing more? Read the patent first, then compare.
  2. Content. Is every field of every record right and complete? One record at a time, against the whole patent.

Coverage comes first. Checking fields in a file with missing records is wasted work.

Three phases

PhaseClaudeYou
1 · Countreads, lists, reconciles, flagsdecide flags, order fixes
2 · Contentverifies each record, flagsdecide flags, order fixes
3 · Decidesemi-final: re-derives every field, corrects. Final: two subagents try to fail the goldaccept, declare gold

Phases 1 and 2 flag and stop. Only Phase 3 corrects as it goes. That order keeps a bad correction out of the ground truth.

Every gate has three steps: Claude validates the flags (P7), you decide, Claude applies the fixes (P8). Chapter 9.

Three tracks

Reactions, compounds, pathways. Each track has the same four passes: identify, reconcile, verify records, final check. In every phase, reactions run before compounds, and compounds before pathways, because each depends on the one before.

Where you fit

Claude reads and flags. You decide. Nothing changes in the gold until you say so.

Two caveats. No human has read the patent line by line unless you do. And the extraction and the audit are both Claude, so the independent read in Phase 1 is the only defence against a shared misreading. Keep it independent.

Golden Patents Manual2 · Before you start

Chapter 2Before you start

What you need on your machine

  • The repository github.com/yashmstack/patent-extraction, cloned, with the pipeline already run for your patent. You check the output; you do not run the extraction.
  • Claude Code, installed and signed in.
  • The prompts in prompts-for-gold/. Read its README once.
  • The findings workbook GOLDEN-DATASET-FINDINGS.xlsx, with a sheet for your patent (columns in Chapter 10).

What you need to know

  • Enough organic chemistry to tell a reactant from a solvent, a range from a point value, and two names for one compound from two compounds.
  • How to read the enriched markdown. Every line has a number, Chinese lines are followed by an indented > EN: translation, and drawings arrive as [IMAGE_EXTRACT: …] blocks carrying SMILES read off the page.
  • That the patent, not the pipeline and not the schema, is the standard. If the patent says it and the file cannot hold it, that is a finding, never a reason to drop it.

The PDF is for you. When a value looks wrong in the markdown itself, open the page in the PDF and look. The markdown came from a vision pass over scanned pages and can be wrong in ways Claude cannot see, because Claude reads the markdown.

Set up the folder

Open a terminal at the repository root and run:

cd runs/<PATENT_ID>

Golden Patents Manual3 · Process map  ·  4 · Rules

Chapter 3The process map

Chapter 4Rules that hold on every pass

These are the rules the prompts enforce. They are here so you can tell when Claude is breaking one, and so you do not break one yourself while deciding flags.

  1. The identification pass never opens the extraction output. Once a reader has seen the answer it finds the same things, and its count is worthless. In one session the same model produced counts of 48, 54 and 56 depending on what it had seen. If Claude admits it has seen the JSON, start a fresh session.
  2. Reconcile by identity, never by number. Two files can hold 54 records each and disagree about half. DMF and N,N-dimethylformamide are one compound. Match on what reacts and what forms, not on labels or counts.
  3. Flag, do not fix, in Phases 1 and 2. Fixing happens only after you have reviewed the flags. Phase 3 corrects as it goes, and logs every change.
  4. Never treat the pipeline's behaviour as correct. It is the thing being measured. Look up what a field is defined to hold; never conclude a value is absent for a good reason because the pipeline left it out.
  5. A null is not evidence the patent is silent. Every empty field is a question. Checking is the only way to tell an absent value from an uncaptured one.
  6. Prose is not capture. A value sitting only in notes or a *_text field is invisible downstream. It is still a finding.
  7. Never withdraw a finding because the schema has no field. Flag it. If it matters, the schema is extended. The gold must be more complete than the pipeline, not equally lossy.
  8. A range reaches the JSON as two numbers. Min and max, with open bounds keeping their side. A single float holding one end of a range is a loss that looks like a value.
  9. A step told twice covers itself. Where the claims and the summary both record one step, a value present on one is not missing from the other. Read twins together.
  10. List every item individually. If there are 43 matches, the table has 43 rows. Ranges of rows hide exactly what you came to check.
  11. Log as you read. Passes as well as failures, so the work can be checked later by someone who was not there.

Chapter 5 · Phase 1The count: does the file hold everything the patent describes?

Four prompts, two per track. The odd-numbered prompt reads the patent alone and writes an independent list. The even-numbered prompt opens the JSON and reconciles the two by identity. You close the phase by deciding every flag.

Open a second fresh session, or a context-free subagent, that has also not seen the JSON. Give it the markdown and the list and ask it to confirm the count, find anything the list missed, and challenge anything on it that is not a real transformation. Reconcile the two lists yourself. Only a list that has survived a second independent reader goes into P2.

Gate 1b · Validate, decide, fix

Validate (P7): run the findings validator over the Missing, Extra and Wrong rows. It re-reads each cited line and marks the row confirmed, withdrawn with a reason, or needs-decision. Decide: for each confirmed Missing row, is it a genuine transformation? Order it added. For each Extra row: false record or duplicate? Remove, or merge if it is a strict subset of its twin, or keep with a note if it is a real retelling that carries substance. For each Wrong row, order the correction. Write every decision in the workbook. Fix (P8): only then tell Claude to apply the decided changes, back up first, log each against its id, and re-run the three counts to prove the file now matches the list.

Gate 1c · Re-verify the compound list

Same as Gate 1a: a second reader that has not seen the JSON confirms the count and the identities. Pay particular attention to one substance under several names, and to isomers sharing a formula, which are two compounds, not one.

P4

Reconcile the list against compounds.json

compounds
Paste
prompts-for-gold/4-compounds-reconciliation.md, after P3 is written down.
Claude does
Record by record, matches on identity using aliases as well as identifier. Finds what the file has that the list has, what is in the file and not the patent, and what the patent names that the file does not hold. Flags duplicates: one substance written several times, once per naming form.
You receive
The same three tables and three counts. Duplicate groups listed with the records in each group and whether they genuinely differ in role or charge.

Gate 1d · Validate, decide, fix

Same three steps. The two decision families that dominate here are the ones from the sketch on the desk: duplicates and chemical structure. Missing compounds are added, class terms included. Duplicates are merged losslessly only when nothing distinguishes them; a substance the patent charges in two roles or two sections stays split, and the reason is written into the record. Never merge on molecular formula: two isomers are two compounds. Log, then P8, then re-count.

Phase 1 is closed when

  • Both independent lists exist, dated, each confirmed by a second reader.
  • Every Missing, Extra and Wrong row has a decision in the workbook.
  • The ordered fixes are applied, backups exist, and a re-count shows matched = list, missing = 0, extra = 0 apart from rows you closed by decision.
  • Every identifier that reactions.json references resolves to a record in compounds.json.
Golden Patents Manual6 · Phase 2 · The content

Chapter 6 · Phase 2The content: is every field of every record right?

Phase 1 fixed the count. Now each record is checked in full. The unit of work is one record and one complete reading of the patent. If the file has 69 records, the patent is read 69 times, each time holding a different record in mind. This phase flags only.

The loop Claude runs, for every record

  1. Open the file and read the schema actually present, so every field is judged by what it is defined to hold.
  2. Take record i, starting at 0, in file order. Keep the index visible in every report so no record is skipped.
  3. Understand the record: what it claims to be, what reacts, what forms, under what conditions.
  4. Read the whole markdown, end to end, asking of every line whether it says anything about this record. Not only the cited lines: the charge is in the example, the range in the claims, the reason in the summary, the structure in a drawing, the meaning of R somewhere else.
  5. Compare. Is every value correct? Is anything the patent says about this record missing? Is anything in the record unsupported? Is the record rich, carrying everything the patent gives and not the minimum?
  6. Do steps 3 to 5 a second time. The second pass catches what the first missed.
  7. Next record. When the last is done, return to 0 for a final sweep of the whole file.

What "read carefully" means here

Read normally first, for meaning: what the step is for, what a phrase refers back to, what a drawing shows. Then do the checkable things alongside. Count how many times the patent states a thing and check the file holds that many. Treat every quotation field as a claim and find the exact string. Line identical situations up side by side across records; most inconsistency is invisible one record at a time. Where a check can be mechanical, make it mechanical: counting, string matching and cross-record comparison are what a reader does worst and a short script does perfectly.

Gate 2 · Validate (P7), decide, fix (P8)

Run the findings validator over every P5 and P6 row first; a flag on a 1,100-line patent is sometimes a misread, and you should not spend a decision on it. Then work the confirmed and needs-decision rows top to bottom. For each row choose one decision from Chapter 9: fix as flagged, fix differently, keep and close by decision, add a field, or leave unresolved with both readings recorded. Where a field is needed that the schema lacks, decide now whether to extend the schema; the gold is allowed to hold more than the pipeline, never less. When every row has a decision, run P8: Claude applies the decided fixes in one pass, backs up first, logs each change against its finding id, and re-validates the JSON against the schema.

Phase 2 is closed when

  • Every record has an entry in the audit log, pass or fail.
  • Every issue is a workbook row with a decision.
  • Ordered fixes are applied and logged, with a backup taken before.
  • The files validate against their schemas, extended where you decided to extend.
Golden Patents Manual7 · Phase 3 · Semi-final and final verification

Chapter 7 · Phase 3Semi-final and final verification: is it actually gold?

Two checks close the work. The semi-final verification is a prompt that assumes nothing: it walks every field of every record, asks where the answer comes from, and corrects as it goes. The final verification is two subagents with no context, each told to try to fail the gold. If neither can, it is gold.

Two kinds of field, checked two ways

A field the patent must answer (a mass, a temperature, a compound, a yield) is checked against the page. A field the model generates (reaction class, mechanism type, tags, confidence) is checked against the chemistry and against how the rest of the file treats the same situation. A generated label can be chemically defensible and still wrong, if two identical records carry different values.

P11

Final verification: two subagents try to fail the gold

all tracks
File
proposed 11-all-final-verification.md; today this is done by hand with fresh sessions
Why
A fixing pass introduces defects of its own. On one finished patent four of the last eight defects were introduced by the annotation, not the extraction, and only a reader with no memory of the fixes caught them.
Claude does
Launches two subagents with no context. Each gets only the markdown and the finished files, and one instruction: try to prove this is not gold. Find any value that is wrong, missing or unsupported, with line numbers. They do not see the workbook, the audit log or each other. Their findings are merged into one triage list.
You receive
The triage list, each item with the record, the line, the claim and which subagent raised it.

Gate 3 · Decide the final-verification findings, accept the corrections, declare

Treat the triage list like any other flag list: validate, decide, fix. Then read every correction the semi-final check made against its line numbers. If either subagent found a real failure, the fix goes in and both subagents run again. When neither can fail it, write the acceptance sentence with your name and the date.

Phase 3 is closed when

  • The semi-final checks P9 and P10 each end with the statement "gold", or every unsettled item has your written ruling.
  • The final verification has run, both subagents failed to break the gold, and every item they raised is decided and logged with introduced by filled in.
  • You have read the finished files and the findings yourself, and accepted them, with the date.

Declaring gold is your act, not Claude's. The sentence in the README is "the annotator read and accepted this on <date>". Write what you did and did not do: reading the findings and directing every judgement call is one thing, reading the patent line by line yourself is another, and the README says which.

Golden Patents Manual8 · Pathways track

Chapter 8 · ProposedThe pathways track

A pathway is a chain of reaction records from a key starting material through intermediates to a product, scoped to a section or a route. pathways.json is built on top of the other two files, so it is checked last and its prompts are not yet written. This chapter fixes the shape of that work and proposes the file names, so the prompts can be written to match.

What is different about pathways

A reaction record is judged against the page. A pathway record is judged against the page and against reactions.json: every step it names must resolve to a reaction record, the product of step n must be a reactant of step n+1, and the route must be one the patent actually draws or describes, not one assembled from steps that happen to connect. The independent read therefore lists routes as the patent tells them, scheme by scheme and section by section.

Golden Patents Manual9 · The gate

Chapter 9The gate: validate, decide, fix

Every flagging pass ends with a list and stops. What happens next is the same at every gate: Claude validates its own flags, you decide what survives, Claude applies exactly what you decided. This chapter is that procedure, the five decisions you can make, and the mistakes made before.

P7

Findings validator: are the flags actually right?

all tracks
File
proposed 07-all-findings-validation.md
Input
The open workbook rows from the pass just finished, the markdown, the file under test.
Claude does
For every row: re-reads the cited lines and the twin record, re-checks the arithmetic, and answers one question, is this finding true? Marks each row confirmed, withdrawn with the reason, or needs-decision where the page supports two readings or the answer is a convention rather than a fact. Groups rows that are one decision (the same lost range on seven records).
You receive
The workbook with the validator's verdict on every row and the groups marked. Nothing has been changed in the JSON.

Your procedure, per gate

  1. Read the whole validated list once before deciding anything. Decide groups, not rows, where the validator grouped them.
  2. Open the page for every confirmed and needs-decision row. Read the cited line in the markdown, and when the markdown is the thing in doubt, the PDF. Never decide from the flag's own summary.
  3. Check the twin. A record with a sibling from another section is read with it before anything is called missing.
  4. Decide, one of the five below, and write decision and reason in the row. Skim the withdrawn rows; reopen any you disagree with.
  5. Run P8 when every row has a decision.
  6. Read the diff between backup and result. A fix that touched more than the flag asked for is itself a flag.

The five decisions

DecisionMeaningStatus after
FIXThe flag is right. Apply as described.decided → fixed → verified
FIX-OTHERReal problem, wrong proposed correction. Write the right one.decided → fixed → verified
KEEPThe record is right as it stands. Say why; if the reason is a convention, write it into the record's notes so the next reader does not flag it again.closed by decision
ADD FIELDThe patent states something the schema cannot hold. Extend the schema, describe the field, then FIX.decided → schema → fixed
UNRESOLVEDTwo readings, no way to choose from the page. Record both in notes. Never average them.open, both readings

A flag is never deleted. A wrong flag is closed as withdrawn with the reason, by the validator or by you, because a withdrawn flag teaches the next reader as much as a fixed one.

P8

Apply the decided fixes

all tracks
File
proposed 08-all-apply-decided-fixes.md
Input
The workbook rows with status decided, and nothing else. A row without a decision is not touched.
Claude does
Copies the file to audit/<file>.BACKUP-pre-<gate>.json. Applies each decided row exactly as written, and only that. Writes a note on the record where the decision was KEEP or ADD FIELD. Re-validates against the schema, re-runs the mechanical counts and the identifier join, and logs every change against its finding id.
You receive
The change log, one line per finding id, and the diff summary: records touched, fields touched, counts before and after.

Decisions that come up on every patent

SituationUsual ruling
One step told in claims, summary and descriptionKeep a record per section when each carries substance the others lack. Merge only strict subsets.
One substance, several namesOne record; other names go to aliases. Original-language names are kept as aliases, never dropped.
One substance, two roles or two charges in different sectionsKeep split. Merging destroys a fact.
Two compounds, one molecular formulaTwo records. Formula is never an identity key.
Drawn structure disagrees with the nameCheck the PDF drawing atom by atom. The drawing usually wins over a machine-rendered name; record which you followed and why.
Range stored as one numberFIX to min and max; point field null. Open bound keeps its side, other end null.
Value only in prose or notesFIX into a structured field, or ADD FIELD.
Patent's own arithmetic or printing is wrongKEEP as printed, contradiction written into notes. Never silently correct the patent.
Machine translation names the wrong compoundFollow the original-language text; keep the wrong rendering as an alias with a note.
Field is general knowledge, not in the patentAllowed, but the README must say the field is not a reading of the patent.

Mistakes already made once

  • Letting the identification reader see the JSON. The count moved by eight.
  • Merging on molecular formula and fusing two isomers into one record.
  • Reading "below 10%" as a yield of 10.
  • A fixing pass marking exact values approximate, and assigning an analytical method by section adjacency. Caught only by the final verification.
  • Taking a wrong OCR of the product name at face value. It named a different registered herbicide.
Golden Patents Manual10 · The audit trail

Chapter 10The audit trail: files, workbook and templates

Gold without a trail is an opinion. Every list, flag, decision and change lives in audit/, and a reader who was not there must be able to reconstruct why every record is the way it is.

Chapter 11Finishing: definition of done and hand-over

Definition of done, per patent

  • Phase 1, 2 and 3 closed for reactions and for compounds, per the close-out boxes in Chapters 5 to 7. Pathways likewise once P12 to P15 exist.
  • Every workbook row has a decision and a status other than open, or is marked UNRESOLVED with both readings in the record's notes.
  • Both JSON files validate against their schemas with zero errors. If fields were added, the schema file is committed alongside and each new field carries a description saying what it holds and why the original could not.
  • Every identifier referenced by reactions.json resolves to a record in compounds.json. Every reaction referenced by pathways.json resolves to a record in reactions.json.
  • The final verification (P11) has run and neither subagent could fail the gold.
  • audit/README.md written from the skeleton, with counts, additions, merges, splits, caveats and the acceptance sentence.
  • RUN-NOTES.md records anything a future reader would otherwise rediscover the hard way.

Hand-over

  1. Copy input/pdf/<ID>.pdf, the enriched numbered markdown, output/reactions.json, output/compounds.json, output/pathways.json and the whole audit/ folder into goldenPatents/<PATENT_ID>/ under input/, output/, audit/.
  2. Add the patent's row to the table in the root goldenPatents/README.md: id, record counts, state. Add its paragraph below, in the form the existing entries use: what the patent is, what the gold holds, what was changed and why, what is deliberately not here.
  3. Commit. The commit message names the patent and the acceptance date.

Working across sessions

Context runs out. Before a session ends, ask Claude to write where it is (phase, prompt, record index, open flags) to RUN-NOTES.md. The next session starts by reading that, the independent list, and the audit log for the current pass. An identification pass that is interrupted is restarted from the top in a fresh session; a verification pass resumes at the recorded index.

Working in parallel

The reactions and compounds tracks are independent through Phase 2 and can run in two sessions at once. They meet at Gate 2, because a compound added or merged changes what a reaction record's identifiers resolve to. Do not run Phase 3 on either file until Phase 2 is closed on both.

When the markdown is wrong

Claude reads the markdown, not the PDF. When a flag makes you suspect the markdown itself, look at the PDF page. If the vision pass misread something, the fix belongs in input/ (the vision JSON and the regenerated markdown), it is written up in RUN-NOTES.md, and any records that depended on it go back through P5 or P6. The original-language text is authoritative; the machine English is a convenience.

The one sentence to remember

Claude reads and flags. You decide and log. Nothing enters the gold that you did not decide, and nothing you decided is without a line number.

Appendix BGlossary

goldA file every record of which meets the five conditions in Chapter 1, accepted by a named person on a date.
extractionThe pipeline's output, the JSON under test. Never a standard.
enriched numbered markdownThe patent as text, one number per line, original language followed by an indented English line, drawings as IMAGE_EXTRACT blocks. The only source Claude reads.
recordOne object in a JSON array: one reaction, one compound, one pathway.
identifierThe compound name a record is keyed on. The join between reactions.json and compounds.json, matched on identifier or alias.
aliasAnother name for the same substance on the same record: the original-language string, a synonym, a SMILES, an InChIKey.
described vs performedA reaction told in prose (claims, summary, description) versus one actually run in an example with charges and a yield. Described repeats are one entry; performed repeats are one each.
twinTwo records of one step from different sections. Read together; they cover each other.
splitOne substance deliberately held as two records because it plays two roles or is charged two ways. Disambiguate on role and section.
class termA word the claims recite in place of a substance: "an oxidant", "a base". Recorded as a compound with no structure.
rangeTwo numbers. Stored as min and max; the point-valued field stays null. An open bound has one side null.
generated fieldA label the model assigns (reaction class, mechanism, tags). Checked against chemistry and against sibling records, not against the page.
flagA finding raised by a pass. Becomes a workbook row. Never deleted; withdrawn with a reason if wrong.
gateThe point at the end of a phase where you decide every flag before anything changes.
closed by decisionA flag you ruled KEEP, with the reason written into the record and the workbook.
findings validatorThe pass (P7) that re-checks every flag against the page before you see it, and marks it confirmed, withdrawn or needs-decision.
semi-final verificationThe prompt (P9, P10) that re-derives every field of every record and corrects as it goes.
final verificationTwo subagents with no context (P11), told to try to fail the gold. If neither can, it is gold. The defence against defects the fixing passes introduced.
context-free readerA fresh Claude session or subagent that has seen none of the earlier work, used to re-verify a list or a finished file.
